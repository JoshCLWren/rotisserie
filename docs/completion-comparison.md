# Read-only same-view completion comparison

This issue #29 slice tests one question: would the current ComicPile code allow
this exact PR head to merge, and would the existing Rotisserie completion
controller select it? It changes neither system's approval or merge rules.
It supplies a captured-data adapter and a public caller, not live host acquisition
or production merge enforcement.

ComicPile main was fetched read-only on 2026-10-09 at
`8692c718458282af9300edffce72035145ff6655`. The archived source remains
`2dc9b675e1a828b526f074c5f5c151293dedcdee`. The checked-in source files under
`examples/completion-comparison/source/` are byte-identical evidence from the
refreshed commit, stored as compressed `.txt.gz` so they cannot be imported or activated.
Decompression recovers the exact source bytes, including original whitespace;
the integrity check hashes those bytes, not a reformatted copy.
`completion_source.py` pins their SHA-256 digests in reviewed code. A different
upstream SHA or changed source bytes refuses comparison until a new audit and
pin update. Supplying a rewritten manifest cannot authorize different code. Before an
observational run, the adopter must freshly fetch upstream and supply that SHA;
the CLI does not contact GitHub to establish freshness. The example caller uses
the audited fixture pin. A fresh SHA outside the supported pin fails closed.

## Try the public caller

```sh
uv sync --locked
uv run python examples/completion-comparison/caller.py
```

The caller uses only the installed `controller-completion-compare` CLI. It puts
its journal in a temporary directory and does not initialize graph state:

```sh
rotisserie --config operator.toml controller-completion-compare \
  --capture capture.json --capture-digest EXACT_SHA256_OF_CAPTURE_BYTES \
  --source-sha 8692c718458282af9300edffce72035145ff6655 \
  --source-directory examples/completion-comparison/source
```

The capture may be streamed with `--capture -`. There is no apply flag.
Exit 0 means the normalized completion eligibility agrees; 3 means a deliberate
safety difference or unexplained divergence; 2 means invalid scope, contract,
source pin or capture integrity. A matching held decision is not permission to
merge. The output carries the source's actual authorization and gate results,
its ordered reads and suppressed label-demotion requests, the generated public
version-1 completion view/request, and `CompletionController.tick(apply=False)`'s
versioned result. These inputs also work with `controller-completion-plan`.

`comparison.json` is generated by running both paths on the exact bytes of
`capture.json`. Tests regenerate it and compare the complete result. The fixture
is synthetic; its issue/PR numbers and trust assertions are examples, not claims
about live ComicPile. No production parity observation or cutover is claimed.

## One capture, two decisions

Version 1 requires one configured repository, one selected PR and expected head,
all linked/prerequisite issues and competing implementations, captured comments,
required checks with names and revision, host reviews, inline comments/thread
state, exact main SHA and its workflow runs, reachable contributor heads,
leases/receipts, explicit capacity/backlog, liveness, and configuration.
No independently authored Rotisserie graph or legacy decision is accepted.
The PR base repository must match the configured target; fork heads do not
change that base identity. The CLI requires its repository and worker inventory
to match the operator allowlist/configuration.

Separate `complete`, `trusted`, and `observed_at` records cover graph/capacity,
comments, reachable lineage, checks, host reviews, inline comments, threads,
main-health and global liveness. All required reads must include pagination,
identity resolution, latest verdicts and unresolved activity. Missing or failed
reads must remain missing or carry false attestations. A partial page or unknown
worker cannot become a trusted empty result. Comment IDs must be unique and in
ascending host order; ambiguity holds. Capture producers must separately prove
that every recorded contributor belongs to the reachable implementation lineage;
markers alone cannot prove reachability. The adapter checks recorded heads
against the captured reachable set and holds on incomplete lineage reads.

These are caller assertions in a fixture contract. This code cannot authenticate
a capture producer or certify a production-consistent host snapshot. A production
acquirer must supply that guarantee before any separate mutation adapter exists.
Captures must be secret-free and bounded to 1 MiB. Exact raw capture bytes,
configuration included, are hashed. The graph token and comparison binding bind
the capture digest and exact source SHA/file digests; changed inputs cannot reuse
old parity evidence. Adopters must also pin the Rotisserie package/caller version.

The source interpreter loads only an explicit list of reviewed functions and
constants through AST extraction. Module imports, entrypoints, worker/repair
loops, contribution recording, subprocess/network modules and post-merge code
are absent. Its read routes accept only the captured selected PR's known reads.
The source's unauthorized-ready path requests label demotion; the replacement
records that request without changing labels. Unknown commands fail. Merge is
never callable. UNKNOWN mergeability is inspected once against this immutable
capture, with the same retry result as exhausting the source's bounded polls;
there is no sleep or changing-host loop.

The machine-readable `mutation_boundary` records the existing bounded/CAS,
head, provenance and uncertain-retry obligations without claiming enforcement.
`source_classification` separately names excluded adopter and post-merge work.

The source path keeps the working sequence: main-health summary, ready-head
semantic authorization, expected-head comparison, mergeability/open/draft check,
required PR checks, then current-head host review/thread blockers. The actual
mechanical interpreters are reused to translate host observations into named
readiness checks rather than rewriting the working gate logic. The existing
Rotisserie controller keeps its own established planning sequence. Its required
CI set is explicit and exact; missing names or duplicate rows cannot disappear.
The source workflow's `--match-head-commit` is pinned as evidence, never executed.
This comparison proves a planned head guard, not a host transaction or full-view CAS.

## Machine-readable differences

`matches` compares one declared head's completion eligibility, not the source's
wording, batching, or all six shadow dimensions. `shared_hold` records when both
stop; the unmodified source results and Rotisserie status explain their stops.
`deliberate_holds` lists differing decisions backed by a concrete existing
Rotisserie safety condition. `safety_holds` also records those proven conditions
when both stop. `unexplained_divergences` catches all remaining mismatches,
including any case where Rotisserie selects work that source refuses. A hold
status alone cannot excuse drift: tests inject incorrect holds into otherwise
valid data and require unexplained divergence. `acquisition_findings` preserves
incomplete/untrusted/stale/ambiguous reads independently of the first stopping gate.

| Source behavior | Existing Rotisserie completion boundary / report reason |
| --- | --- |
| Missing contributor record can accept two independent approvals | Requires a known attested writer and complete exact-head/reachable author records before claiming; `complete_attested_exact_head_producer_and_lineage_required` |
| Branch/body writer excludes that worker but need not be attested | Exact-head review attestations must agree with the declared writer; unknown/contradictory identity holds under the same named reason |
| Approval marker on the first line of a trusted comment is accepted | Established collector requires a whole-body marker; otherwise writer/review evidence is absent and holds |
| Earlier approval remains in `current_head_approvers` after a later non-approve marker | Latest exact-head verdict per worker wins; `latest_semantic_verdict_revoked_earlier_approval` |
| State-only required-check interpreter can pass unnamed/partial contexts | Explicit named required contexts and exact check head; `exact_head_complete_required_context_set_required`, or incomplete-read hold |
| Source reads do not attest a complete fresh repository view | Complete trusted fresh graph, lineage, mechanical reads and liveness required; distinct acquisition/provenance/readiness/liveness holds |
| Ready drain does not claim a full completion lease/receipt | Existing lease, duplicate change and all durable receipt phases fence a new attempt; `bounded_durable_ownership_and_duplicate_fence` |
| Ready drain does not apply this configured completion capacity/human/prerequisite policy | Existing explicit capacity/backlog/participant-idle and human/prerequisite gates hold with separate reasons |

The current source's full contributor-set exclusion is retained, including
workers who repaired earlier reachable heads. The archived single-writer rule
is never used as the golden baseline. Formal GitHub approvals cannot replace
worker semantic approval; current-head change requests and unresolved threads
remain mechanical blockers. Passing SKIPPED/NEUTRAL check states and the source's
complete zero-main-run behavior are preserved, not redesigned here.

## Audited boundaries and remaining work

The refreshed audit compared current and archived review controllers/policies,
contributor-record writing, work-controller contributor reads and worker-specific
ordering, completion/full-completion demand and capacity signalling, ready drain,
post-merge closure and release reconciliation. Selection, ownership, liveness,
capacity and completion planning remain application/domain behavior. Author/App
trust, markers, worker mapping, complete pagination, product labels/eligibility,
ordering, host context names and activity translation stay in adapters/configuration.
The comparison is an entrypoint over that read-only adapter and existing public
completion contract. It does not expand the source's whole dispatcher session.

Workflow-run approval/recovery, migration-lane reconciliation and any preparatory
repair are outside the captured decision slice and never invoked. Product
ordering is the caller's declaration of the single selected PR, not a newly
invented portable ranking. Post-merge linked-issue closure, protected/manual and
acceptance-parent checks, successor checks, release publication and reconciliation
are separately classified post-merge capabilities. They grant no completion
authority. The result explicitly excludes them and cannot be decoded as the
six-dimension adoption `ShadowReport`.

Production durable CAS and host enforcement, live consistent acquisition,
provider bridges, uncertain-completion adjudication/release, post-merge contracts,
and observed execution with rollback/cutover remain follow-on work under #29.
Fixture attestations confer no mutation authority or live adoption approval.
ComicPile, archived evidence, active workflows and the issue-9 canary are unchanged.
Issue #29 remains open.
